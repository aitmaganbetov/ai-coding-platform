# ADR-0030: Self-Hosted сервер — API, аутентификация, RBAC, изоляция проектов, очередь и worker'ы

- Статус: Принято
- Дата: 2026-11-05
- Уточняет: [ADR-0013](0013-queue-and-worker.md), [ADR-0014](0014-api-and-web-ui.md)

## Контекст

S8 переводит платформу из однопользовательского CLI в Self-Hosted сервер (ТЗ §3, §13, §15). Требования:
- endpoints ТЗ §13 с `Idempotency-Key`;
- RBAC на сервере с ролями Owner/Admin, Maintainer, Developer, Auditor, Agent;
- обязательная межпроектная изоляция, каждая операция в журнале с actor, project_id, run_id, временем и результатом;
- ≥10 параллельных заданий (NFR-02);
- аутентификация, TLS, rate limiting (NFR-04).

Приёмка AC-08: два проекта и несколько пользователей подтверждают RBAC и отсутствие утечки контекста.

Оркестратор (S2) уже даёт FSM, checkpoints, leases прогонов, approvals и журнал аудита. Сервер не должен дублировать эту логику.

## Решение

1. **Слои.** Пакет `ai_coding.api` стоит над `workflows` и под `cli` (import-linter):
   - `services.Server` — вся бизнес-логика и проверки прав, без HTTP;
   - `app` — тонкие FastAPI-роутеры;
   - `worker` — очередь и пул.

   CLI `ai-coding server …` и тесты обращаются к тому же `Server`. Права проверяются в сервисном слое, поэтому их нельзя обойти другим транспортом.

2. **Одна серверная БД, оркестратор на проект.** Таблицы S2 (projects, runs, tasks, audit_events …) общие. Для прогона создаётся `Orchestrator` с `project_root` клона и `local_owner=False`. Локальный режим делает пользователя CLI owner'ом проекта. На сервере это было бы повышением привилегий, поэтому здесь членство назначает только `set_member`.

3. **Тип прогона хранится в прогоне.** `kind` и проверенные `params` пишутся в `run.options` (`RunOptions.extra`). Любой worker может пересобрать тот же реестр обработчиков для `execute` и `resume`. Типы: `discover`, `audit`, `develop`, `maintain`. Для `audit` backend на сервере всегда Docker: анализаторы не запускаются на хосте сервера.

4. **Аутентификация.**
   - Пароли хранятся как argon2id (минимум 12 символов) и пересчитываются при входе, если параметры устарели.
   - Токены: `aic_` + 256 бит случайности; в БД только SHA-256, сравнение за постоянное время.
   - Токен может быть привязан к проекту и ограничен ролью сверху (`max_role`); у него есть срок действия.
   - `agent`: только с привязкой к проекту, срок ≤ 24 ч.
   - Токен входа живёт 12 ч.
   - Токен с привязкой к проекту не выпускает новых токенов.
   - Ротация: новый токен с той же областью, старый отзывается сразу.
   - OIDC/SSO — backlog.

5. **RBAC.**
   - Матрица `rbac.MATRIX` связывает роль и право (`Permission`): 13 прав, от `project.view` до `project.delete`.
   - Эффективная роль — `min(роль участника, max_role токена)`.
   - Администратор сервера регистрирует проекты и пользователей. Создать проект может только он, а путь на сервере допустим только внутри `ALLOWED_ROOTS` (иначе — клон по Git URL). Без этого пользователь мог бы зарегистрировать чужой каталог хоста.
   - Developer отменяет только свои прогоны, Maintainer — любые и решает approvals. Auditor читает журнал. Owner управляет участниками, экспортом и удалением. Последнего owner'а убрать нельзя.

6. **Изоляция: «чужое = несуществующее».** Любой доступ к объекту проекта идёт через `Server.require(principal, project_id, permission)`. Если пользователь не участник проекта или токен привязан к другому проекту, ответ — `NotFound`, тот же, что и для отсутствующего объекта. Так нельзя перебором узнать идентификаторы чужих прогонов. `403` получает только участник с недостаточной ролью. Прогон, артефакт и находка разрешаются через свой `project_id`, поэтому прямой ссылкой нельзя выйти за проект.

7. **Аудит отказов.** Отказ `access.<право>` с результатом `denied` пишется в отдельной транзакции и не откатывается вместе с запросом. Отказы по чужому проекту записываются без project_id этого проекта: журнал проекта не должен раскрывать посторонних, а событие видно администратору.

8. **Idempotency-Key.**
   - Таблица `idempotency_records` с уникальным ключом (пользователь, ключ) хранит метод, путь, SHA-256 тела и ответ.
   - Повтор возвращает сохранённый ответ с `Idempotent-Replayed: true`. Тот же ключ с иным запросом — `422`.
   - Гонку двух одинаковых запросов разрешает уникальный индекс: второй получает сохранённый ответ.
   - Записи хранятся сутки.

9. **Очередь в БД (ADR-0013).**
   - Таблица `run_jobs`: виды `execute|resume`, состояния `queued|leased|done|failed`.
   - Захват: в PostgreSQL `SELECT … FOR UPDATE SKIP LOCKED`, в SQLite compare-and-set `UPDATE … WHERE state='queued' OR lease истёк`.
   - Lease задания продлевается heartbeat'ом. Истёкший lease возвращает задание в очередь. После `MAX_ATTEMPTS=3` задание помечается `failed`, а «ядовитое» задание не крутится бесконечно.
   - Продолжение после падения выполняет `resume` оркестратора с checkpoint. Effect ledger исключает повтор побочных эффектов.

10. **Worker.**
    - `AI_CODING_SERVER_WORKERS` прогонов на процесс (по умолчанию 10, NFR-02). Каждое задание выполняется в собственном потоке со своим event loop, из пула размером `concurrency`. Обработчики делают и синхронную работу: БД, git, файлы. В общем loop она останавливала бы другие прогоны, а при `serve --with-worker` — сам API. Пул по умолчанию (`min(32, CPU+4)`) не годится: на малом хосте он ограничил бы параллельность ниже NFR-02.
    - Approval переводит прогон в `WAITING_APPROVAL` и освобождает слот. `approve` ставит `resume` в очередь, когда ожидающих approvals не остаётся.
    - Отмена — флаг прогона, который оркестратор проверяет между шагами.
    - Graceful shutdown: при SIGTERM/SIGINT worker не берёт новые задания и дожидается текущих.

11. **HTTP.**
    - Ошибки в едином JSON-формате; лимит тела 1 МБ.
    - Заголовки безопасности: строгий CSP; для `/api/docs` разрешён только `cdn.jsdelivr.net`.
    - Rate limit: token bucket в процессе, на пользователя/токен и отдельно на вход с IP.
    - `X-Forwarded-For`/`-Proto` учитываются только от `TRUSTED_PROXIES`. HSTS — только по HTTPS. TLS терминирует reverse proxy (ADR-0031).

## Последствия

- Все пути к данным проекта проходят через одну функцию. AC-08 проверяет по REST API для каждого пути, что ответ на чужой объект неотличим от ответа на несуществующий.
- Один и тот же код работает с SQLite (один хост, тесты) и PostgreSQL. Корректность `SKIP LOCKED` проверена в настоящем PostgreSQL: 3 worker'а и 24 задания без дублей.
- **Отклонение от ADR-0013:** порт `TaskQueue` с адаптером Redis не реализован. Очередь в БД покрывает NFR-02 без новой инфраструктуры, Redis остаётся опциональным (ТЗ §4). Rate limiter в процессе: при нескольких репликах API лимит умножается на их число; общий лимитер на Redis — точка расширения.
- **Отклонение от ADR-0014:** клиент Web UI типизирован вручную (`web/src/api.ts`), без генерации из OpenAPI и TanStack Query. Это меньше зависимостей; дрейф API ловят тесты UI и e2e smoke (ADR-0031).

## Альтернативы

- **Проверка прав только в зависимостях FastAPI** — отклонено: CLI `server export` и worker обходили бы их.
- **Отдельная БД на проект** — сильнее изоляция, но сложнее миграции, бэкапы и общий журнал. Изоляция обеспечивается единым `require` и проверена тестом.
- **Celery/RQ** — отклонены в ADR-0013.
- **JWT** — отклонено: нужен немедленный отзыв, а хэш непрозрачного токена в БД даёт его без списков отзыва.
