# ADR-0035: Изоляция выполнения (gVisor, Job Objects) и процесс релиза (SBOM, Sigstore, SLSA)

- Статус: Принято
- Дата: 2026-11-05

## Контекст

- **B-805:** контейнер изолирует процесс, но системные вызовы кода проекта обрабатывает ядро хоста. Уязвимость ядра — путь наружу.
- **B-206:** на Windows у локального executor'а не было лимитов, потому что rlimits есть только в POSIX.
- **B-802:** ТЗ §12 требует подписанных и проверенных артефактов, SBOM, provenance и журнала изменений.
- **B-806:** релиз v2.1.

## Решение

1. **gVisor — по выбору оператора.**
   - `execution.docker.runtime` передаётся в `docker run --runtime`. При `runsc` код проекта работает поверх ядра gVisor в пространстве пользователя.
   - По умолчанию остаётся runtime демона: gVisor нужно установить на хост worker'а, и он медленнее на тяжёлом I/O.
   - Если демон не знает runtime, это явная ошибка, а не тихий откат на runc.
   - CI ставит `runsc` из закреплённого релиза с проверкой SHA-512 и проверяет песочницу на gVisor. Пропуск запрещён.

2. **Job Object на Windows.** Каждая команда локального executor'а выполняется в Job Object (`ctypes`). Он ограничивает:
   - память всего дерева процессов — сильнее POSIX-лимитов, где память без cgroups не ограничить;
   - суммарное время CPU и число процессов.

   `KILL_ON_JOB_CLOSE` завершает всё дерево при закрытии задания, в том числе по таймауту. Процесс назначается в задание сразу после запуска, а дочерний процесс, созданный до этого мгновения, остаётся вне задания: asyncio не создаёт приостановленный процесс. Поэтому недоверенный код — только в Docker-песочнице.

3. **Релиз по тегу `vX.Y.Z`**, workflow `release-platform.yml`:
   - **сборка:** тег обязан совпадать с версией пакета; wheel, sdist, SBOM, `SHA256SUMS`;
   - **образ:** публикуется в GHCR, подписывается keyless через cosign и Sigstore OIDC, получает SLSA provenance и SBOM attestations в реестре;
   - **публикация:** окружение `release` требует одобрения человека. Контрольные суммы проверяются повторно, к файлам добавляются attestations и bundles cosign. GitHub release остаётся **черновиком**, его публикует maintainer;
   - **PyPI:** trusted publishing, только при переменной `PYPI_PUBLISH=true` и в окружении `pypi`.

   У каждого job свои минимальные права. `id-token` есть только там, где подписывают, все actions закреплены по SHA.

4. **SBOM.** Генератор `scripts/sbom.py` один и тот же для релиза и тестов:
   - Python — точно по `uv.lock`, только runtime;
   - Web UI — то, что попадает в bundle;
   - образ — Syft по выводу `docker save`, без сокета и без сети.

   Тесты сравнивают содержимое SBOM с lock-файлами.

5. **Версия 2.1.0** совпадает с версией ТЗ. Журнал изменений — `CHANGELOG.md` (Keep a Changelog).

## Последствия

- Проверить происхождение релиза может любой: `gh attestation verify`, `cosign verify` / `verify-blob` ([operations.md](../operations.md) § 8).
- **Тег ставит человек** после merge в `main`, и он же публикует черновик релиза. Агент тег не ставит: это внешнее и необратимое действие.
- **PyPI и окружения GitHub** (`release` с reviewers, `pypi`) настраивает владелец репозитория. Без этого job `release` ждёт окружение, а `pypi` не запускается.

## Альтернативы

- **Ключи GPG для подписи** — отклонено: ключом нужно управлять. Keyless Sigstore привязывает подпись к workflow и тегу.
- **Kata Containers** — отклонено: нужна вложенная виртуализация на хосте worker'а. gVisor работает и без KVM (платформа systrap).
