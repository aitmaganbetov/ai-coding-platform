# ADR-0038: Оркестратор как инструменты агентов чата

- Статус: Принято
- Дата: 2026-11-06
- Уточняет: [ADR-0037](0037-ai-chat-agents.md)

## Контекст

Режимы чата (ADR-0037) задают агенту процесс, но гарантии ТЗ есть только у оркестратора:
- реальные анализаторы в песочнице (§4);
- находки с доказательствами и Quality Gates (FR-06, FR-10, FR-11, §10);
- run'ы с состояниями, контрольными точками и журналом (§5, FR-16);
- согласие человека (§5).

Чат шёл мимо оркестратора: «аудит» в чате был мнением модели. Нужно, чтобы агент чата (Claude Code или Codex на подписке пользователя) ставил задачи оркестратору и работал с их результатами. Ограничения:
- контейнер рабочей области не видит API по сети (только allowlist-прокси наружу);
- права агента не должны превышать права пользователя (§3, роль Agent — минимальные права);
- агент не может утверждать run'ы сам.

## Решение

1. **MCP-сервер `platform`** (`ai-coding-agent mcp`, тот же скрипт, что служба чата) подключается к обоим CLI их штатными средствами:
   - у Claude Code — `--mcp-config` на каждый чат;
   - у Codex — `config.mcp_servers` в `thread/start`.

   Инструменты:

   | Инструмент | Что делает | Разрешение |
   |---|---|---|
   | `info` | Проект, доступные виды run'ов, есть ли у оркестратора ИИ-провайдер | Не нужно |
   | `audit` | Run аудита: `source=workspace` — последний коммит текущей ветки рабочей области, `project` — дерево проекта | Не нужно (файлы не меняет) |
   | `run_status` | Состояние, шаги, ожидающие согласия; `wait_seconds` до 45 | Не нужно |
   | `run_report` | Quality Gates, находки по важности с файлом и строкой, отчёт Markdown | Не нужно |
   | `start_task` | Задача собственным агентам оркестратора (`develop`, `maintain`): ветка или PR в проекте; нужен ИИ-провайдер проекта | Спрашивается в чате |
   | `cancel_run` | Отмена run'а своего пользователя | Спрашивается в чате |

   - Инструменты чтения разрешены заранее (`--allowedTools`, `readOnlyHint`). Поэтому они работают и в режиме плана, и в «Аудите».
   - В «Аудите» MCP-сервер запускается с `--read-only` и не предлагает `start_task` и `cancel_run`.
   - Вопрос Codex перед вызовом MCP (`mcpServer/elicitation/request`) приходит в чат карточкой разрешения. В «Аудите» служба пропускает вопросы своего сервера `platform` (он там только читает) и отклоняет вопросы других MCP-серверов.
   - Утверждать run'ы агент не может: такого инструмента нет. Ожидающие согласия run'ы агент показывает ссылкой `#/runs/<id>`, а чат делает её кликабельной.

2. **Транспорт — почтовый ящик рабочей области:** `<data>/workspaces/<project>/<user>/mailbox`. Папка монтируется только в контейнер этой рабочей области, в `/platform`.
   - MCP-сервер кладёт `<id>.req` (JSON). Для аудита рабочей области он сначала кладёт `<id>.bundle` (`git bundle` текущей ветки).
   - Цикл в процессе API (`AgentBridge`) раз в секунду забирает запрос переименованием (так его не обработают два процесса API) и пишет `<id>.res`.
   - Сеть между контейнером и API не нужна. Ящик работает и в docker-compose (общий каталог данных), и в `serve` без Docker-сервиса.

3. **Личность определяется местом, а не содержимым.** Проект и пользователь берутся из пути к ящику.
   - API действует от имени этого пользователя с его ролью в этом проекте: каждый раз проверяется `workspace.use`, а для каждого действия — его обычное право (`run.create`, `run.create_changes`, `findings.view`…).
   - Run'ы других проектов агенту не видны. Отменить можно только run'ы своего пользователя.
   - Действия агента пишутся в журнал (`workspace.agent`) рядом с обычными `run.create`.
   - Ограничения частоты: 120 запросов в минуту, 30 run'ов в час на пользователя и проект.

4. **Файлы ящика недоверенные** (их пишет контейнер):
   - открываются с `O_NOFOLLOW` относительно дескриптора каталога, должны быть обычными файлами;
   - размер ограничен: запрос до 64 КБ, bundle — до предела загрузки;
   - ответ пишется через временный файл с `O_EXCL` и переименованием, поэтому подложенная ссылка `<id>.res` заменяется, а не используется;
   - читаются только имена `<hex>.req`, неотвеченные и чужие файлы удаляются через час.

5. **Аудит рабочей области проверяет снимок, а не живую папку.**
   - Сервер переносит ветку из bundle (простые данные: ни конфигурации, ни хуков отправителя) во временный репозиторий. Оттуда `git archive` выгружает закоммиченное дерево в `<data>/sources/<project>/<user>/<commit>`: без `.git`, без незакоммиченных правок.
   - Run хранит путь в `options.source`. Это поле задаёт только сервер, не параметры запроса, и worker проверяет, что путь лежит в `sources/<project>`.
   - Шаги проверяют это дерево (`StepContext.tree`: сканеры, стеки, контекст, целостность). Конфигурация, baseline, артефакты и состояние остаются у проекта (`StepContext.project_root`), так что агент не может ослабить правила проверки своей веткой.
   - Снимок допустим только для run'ов, которые лишь читают (`audit`, `discover`). Хранятся последние 5 снимков на пользователя и проект (и все моложе 6 часов). При удалении проекта они удаляются.

6. **Режимы используют инструменты по своему процессу** (подсказки в `WORKFLOWS`):
   - «Аудит» начинает с аудита платформы и строит отчёт на его находках, а своё мнение помечает отдельно;
   - «Разработка», «Сопровождение» и «Создание» перед отчётом коммитят и прогоняют аудит рабочей области (Quality Gates);
   - «Модернизация» делает аудит до и после работы и сравнивает;
   - `start_task` агент вызывает только по просьбе пользователя.

## Последствия

- Чат на подписке пользователя получает детерминированные проверки ТЗ: находки реальных инструментов с доказательствами, Quality Gates и run'ы в журнале. Для этого не нужен ИИ-провайдер у оркестратора.
- Задачи собственным агентам оркестратора (`develop`, `maintain`) можно ставить из чата, если у проекта настроен ИИ-провайдер (API-ключ). Без провайдера агент получает понятный отказ.
- Задержка запроса — до секунды (опрос). Аудит рабочей области проверяет только закоммиченное; об этом агент получает пометку с числом незакоммиченных правок.
- Контейнеры, запущенные до этой версии, не видят ящика: агент получает сообщение «перезапустите среду». Новый образ заменяет контейнер, когда им никто не пользуется.

## Альтернативы

- **Токен API в контейнере и HTTP-запросы к API.** Отклонено: нужна сеть от контейнера к API через прокси (зависит от развёртывания), а токен в среде агента легко утечь (prompt injection).
- **Запросы через WebSocket чата.** Отклонено: работает, только пока открыт браузер, а агент должен работать в фоне.
- **Сделать Claude Code или Codex LLM-провайдером оркестратора.** Отклонено: запросы по подписке пошли бы через автоматический конвейер платформы, что противоречит правилам вендоров. С API-ключом оркестратор и так вызывает API напрямую.
- **Аудит живой папки рабочей области.** Отклонено: результат зависел бы от незакоммиченного состояния, а агент мог бы менять файлы во время проверки. Снимок коммита воспроизводим (NFR-05).
