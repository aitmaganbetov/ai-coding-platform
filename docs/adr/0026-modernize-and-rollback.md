# ADR-0026: MODERNIZE — baseline, план шагов, малые PR, откат

- Статус: Принято
- Дата: 2026-11-05
- Спринт: S6 (B-504)

## Контекст
FR-05: baseline, impact analysis, малые PR, миграционные планы и rollback. ТЗ §2: поэтапная модернизация с откатом.

## Решение
1. **Baseline.** Тесты базового коммита запускаются в песочнице первыми.
   - Красный baseline останавливает прогон: модернизацию нельзя начинать с падающих тестов. Обойти можно только явно, `--allow-red-baseline`.
   - Зелёный baseline делает PASSED обязательным для каждого шага: регрессии запрещены, SKIPPED недостаточно.
2. **Анализ влияния и план.** Planner Agent работает в роли модернизации и использует свою схему `planner.migration.output.schema.json`. На входе:
   - цель;
   - файлы репозитория;
   - релевантный контекст;
   - результат baseline.

   Результат: затронутые файлы, модули и риски, затем шаги `M-NN`. У каждого шага есть файлы, способ проверки, способ отката и риск. Проверки: файлы из анализа влияния существуют, id шагов уникальны, шаг затрагивает не больше 25 файлов.
3. **Утверждение плана.** Человек утверждает конкретную версию `p<n>-<sha8>`. Используется тот же неотключаемый gate, что и для ТЗ в CREATE (`spec_approval`, правило `modernize.plan`).
4. **Шаг = прогон = ветка = PR.**
   - Один прогон выполняет один шаг через тот же цикл, что DEVELOP.
   - Ветка шага: `ai/modernize-<slug>-m-NN`.
   - Коммит один; затем проверка; затем PR (опционально).
   - Следующий шаг: `--continue RUN` берёт утверждённый план из выхода шага (повторное утверждение не нужно) и снова прогоняет baseline на текущей базе.
5. **Откат** (`--rollback RUN`).
   - Если коммит шага (по trailer `AI-Coding-Run`) уже в базовой ветке — после merge commit или squash, — создаётся ветка `ai/revert-<id>`. На ней выполняется `git revert` всех таких коммитов (для merge commit — `-m 1`) **одним коммитом** с trailer `AI-Coding-Revert` и `AI-Coding-Reverts`. Дальше — опционально PR.
   - Если шаг не влит, откат — это закрытие PR и удаление ветки; платформа так и сообщает, ничего не меняя.
   - `revert` запрещён на защищённых ветках и выполняется без hooks.

## Последствия
- **Плюс:** каждый шаг модернизации мал, проверен тестами без регрессий и обратим.
- **Ограничение:** шаги выполняются от базовой ветки, а не стопкой (stacked PR). Следующий шаг логично запускать после merge предыдущего. Пример — в `docs/develop.md`.
