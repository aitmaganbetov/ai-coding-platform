# ADR-0046: ИИ-провайдер оркестратора из веба

- Статус: Принято
- Дата: 2026-11-06
- Уточняет: [ADR-0009](0009-llm-providers-optional-ai.md), [ADR-0023](0023-llm-adapters-routing-cache.md); общие настройки и секреты проекта — те же, что в [ADR-0043](0043-github-actions.md) и [ADR-0048](0048-deploy-adapter.md)

## Контекст

Провайдер, модель и бюджеты агентов оркестратора задавались только в `.ai-coding.yml` проекта. Ключ задавался именем переменной окружения сервера (`api_key_env`). Чтобы подключить OpenAI или Anthropic, владелец проекта правил файл в репозитории и просил администратора добавить переменную в окружение сервера и перезапустить его. Страница «Модели» могла только показать настройки.

Общие настройки и зашифрованные секреты проекта уже есть: таблицы `project_settings` и `project_secrets`, право `PROJECT_SETTINGS`, `SecretField` в вебе. Их используют GitHub Actions (ADR-0043) и деплой (ADR-0048).

## Решение

1. **Раздел `ai` настроек проекта.** Поля: `enabled`, `provider` (openai | anthropic | ollama | vllm), `model`, `base_url`, `routing` (агент → модель того же провайдера), `fallback` (до пяти моделей), `budgets`, `private`. Все поля необязательные.
   - Отсутствующее поле наследует `.ai-coding.yml`.
   - Заданное поле действует поверх файла для запусков на сервере: API и воркер читают конфигурацию через `ProjectService.project_config` → `config_overrides`.
   - Если в вебе выбран другой провайдер, адрес, ключ, маршруты и резервные модели из файла не наследуются: они относились к старому провайдеру.
   - Результат проверяется как обычная конфигурация (`AICodingConfig`). Настройки, которые не подходят к файлу, сервер не принимает (422).
   - Если файл изменился и старые веб-настройки к нему больше не подходят, действует файл. `GET /ai` сообщает об этом (`valid: false`, `error`).
   - Локальный CLI по-прежнему читает только файл.

2. **Ключ — только для записи.** Ключ хранится как секрет проекта `ai.api_key`: AES-256-GCM под `AI_CODING_SERVER_SECRET_KEY`, задаётся через `PUT /secrets/ai.api_key` и `<SecretField>`. Его нет в ответах, событиях аудита, журналах, параметрах и артефактах запусков. Пройти к провайдеру ключ может только так:
   - эффективная конфигурация получает синтетическое `api_key_env` вида `AI_CODING_PROJECT_<id>_API_KEY`. Такой переменной нет ни в одном окружении, в `os.environ` ключ не попадает;
   - `config_overrides` регистрирует под этим именем ленивый источник в процессном реестре `llm_factory.CREDENTIALS`;
   - `llm_factory.api_key(env, name)` берёт значение сначала из окружения, затем из реестра. Секрет расшифровывается только в момент создания провайдера;
   - провайдер, как и раньше, добавляет ключ в `default_redactor`.

   Если в вебе выбран тот же провайдер, что в файле, а ключ в вебе не задан, действует переменная из файла. В ответе API показывается только её имя.

   **Чужие имена запрещены.** Реестр общий для процесса, а имена в нём предсказуемы. Поэтому `config_overrides`, через который проходят все серверные пути к модели (запуски, чат-инструменты, `/ai/test`), отвергает конфигурацию, где `api_key_env` маршрута называет переменную `AI_CODING_*`, кроме собственного веб-ключа проекта. Ответ — 422, а `GET /ai` возвращает `valid: false`. Иначе `.ai-coding.yml` любого проекта мог бы указать имя веб-ключа другого проекта или секрет самой платформы (`AI_CODING_SERVER_DATABASE_URL`, `AI_CODING_SERVER_SECRET_KEY`, `AI_CODING_S3_*`) вместе со своим `base_url` и получить значение в заголовке запроса к модели. Есть ли у сервера такая переменная, `GET /ai` тоже не сообщает.

3. **Private Mode.** `private: true` означает `security.network: local-only` с пустым allowlist. Облачные провайдеры в этом режиме запрещены правилами конфигурации.
   - `private: false` при включённом облачном провайдере добавляет в allowlist только хост провайдера. Остальная политика сети проекта не меняется.
   - Удалённый `base_url` принимается только по https. http разрешён лишь для локальных хостов.

4. **Проверка подключения.** `POST /ai/test` и `GET /ai/models` делают настоящий вызов списка моделей провайдера (`/models`, у Anthropic `/v1/models` с `x-api-key`) с эффективными настройками.
   - Политика сети проекта действует и здесь.
   - Ссылочно-локальные, служебные и метаданные-адреса (`169.254.0.0/16`, `metadata.google.internal` и т. п.) не вызываются.
   - Редиректы не выполняются.
   - В разбор идёт не больше 1 МБ ответа провайдера, тексты ошибок чистятся от ключа.
   - Результат проверки пишется в аудит как `project.ai.test`: провайдер и модель, без ключа.

5. **Доступ.**
   - `GET /projects/{id}/ai` — все участники проекта (`PROJECT_VIEW`).
   - Изменение, проверка и список моделей — владелец и мейнтейнер (`PROJECT_SETTINGS`).
   - Право проверяется до чтения тела запроса и до обращения к провайдеру. Посторонний получает 403/404.
   - `PUT` защищён номером версии (409 при одновременном изменении).
   - Изменение пишется в аудит как `project.settings`.

6. **Страница «Модели».**
   - Блок «Действует сейчас» и «Проверить подключение» с результатом.
   - Переключатель ИИ, карточки провайдеров, модель (список от провайдера или свободный ввод), адрес для Ollama и vLLM, ключ через `SecretField` (для Ollama скрыт), Private Mode с пояснением.
   - Модели по агентам, резервные модели и бюджеты.
   - У каждого поля метка «из .ai-coding.yml» или «задано в веб» и действие «вернуть из файла».
   - Остальным ролям страница доступна только для чтения.
   - Графики расхода и таблица «агент → модели» остаются.
   - Отдельно сказано, что чат Claude Code и Codex работает по подписке пользователя и этими настройками не управляется.

## Последствия

- Владелец подключает провайдера без правки репозитория и без доступа к серверу. Ключ хранится один раз, зашифрованным.
- Запуски на сервере и `ai-coding run` локально могут работать с разными провайдерами. Страница показывает источник каждого поля.
- Ключ из веба работает только при заданном `AI_CODING_SERVER_SECRET_KEY`. Без него страница предлагает переменную окружения, как раньше.
- Проверки:
  - интеграционные тесты с фейковыми серверами OpenAI и Anthropic: ключ доходит до провайдера и отсутствует в ответах, аудите и журналах; провайдер, эхом вернувший неверный ключ, не раскрывает его; Private Mode; метаданные-адреса; RBAC; переменная из файла; версия;
  - модульные тесты наложения настроек и реестра ключей;
  - компонентные тесты страницы: редактирование и только чтение, `SecretField`, результат проверки, ключ не остаётся в DOM.

## Альтернативы

- **Класть ключ в окружение воркера** (`os.environ` или `env` шага). Отклонено: ключ виден дочерним процессам инструментов и песочнице и может попасть в дамп окружения.
- **Писать изменения в `.ai-coding.yml` репозитория.** Отклонено: это коммит в код пользователя, а ключ в файл класть нельзя.
- **Проверка подключения полным запросом к модели.** Отклонено: запрос платный и медленный. Списка моделей достаточно, чтобы проверить ключ, адрес и сеть.
