# ADR-0033: Egress-allowlist песочницы, Playwright и k6 для проектов пользователей

- Статус: Принято
- Дата: 2026-11-05
- Уточняет: [ADR-0018](0018-executors-implementation.md), [ADR-0027](0027-project-tools-and-offline-data.md)

## Контекст

ТЗ §12: «режим local-only полностью запрещает egress», исполнение — в изолированных контейнерах. До S9 шаги песочницы с сетью (установка зависимостей, обновление пакетов) запускались с `--network bridge`. Политика проверяла список хостов перед запуском, но контейнер мог обратиться куда угодно. Скрипт установки из зависимости мог отправить исходный код на любой адрес (B-205).

B-603 добавляет инструменты, которым сеть нужна по сути:
- k6 нагружает тестируемую систему;
- Playwright устанавливает зависимости и запускает браузеры.

## Решение

1. **Шаг с сетью получает список хостов** (`CommandSpec.egress`). Executor на время шага создаёт:
   - `--internal` сеть Docker без маршрута наружу, контейнер получает `--dns 0.0.0.0`;
   - прокси-контейнер — единственный выход. Он работает в закреплённом образе Python runtime от `nobody`, только для чтения, без capabilities и с лимитами.

   Прокси пропускает `CONNECT :443` и HTTP `:80` к хостам из списка по правилам политики. Запись `host:port` разрешает ровно этот порт.

   Обычный HTTP прокси пересобирает сам, по одному запросу на соединение:
   - заголовок `Host` обязан называть разрешённую цель — иначе за разрешённым адресом CDN можно обратиться к другому сайту (domain fronting);
   - тело запроса читается только по `Content-Length`, `Transfer-Encoding` не пропускается;
   - upstream получает `Connection: close`, и больше ничего от клиента до него не доходит, то есть второй запрос по keep-alive-соединению невозможен (исправлено после ревью кода).

   Каждое решение пишется в лог JSON-строкой, а отказы добавляются в stderr шага, чтобы причина сбоя установки была видна. После шага сеть и прокси удаляются.

2. **SSRF.** Если разрешённое имя разрешается в приватный, loopback или link-local адрес — например, сервис метаданных облака или внутренние сервисы через DNS rebinding, — прокси отказывает. Исключение: хосты, которые оператор назвал сам (`performance_hosts` для k6, `egress_private`), потому что staging часто внутренний. Для хостов реестров исключения нет.

3. **Кто получает список хостов:**
   - установка зависимостей инструментов проекта и тестов в песочнице — хосты реестра по стеку;
   - обновление зависимостей (MAINTAIN) — реестр пакета;
   - k6 — хосты тестируемой системы.

   `ai-coding tools pull` остаётся явной загрузкой баз оператором без ограничений.

4. **Playwright.**
   - Работает в образе `mcr.microsoft.com/playwright` по digest с браузерами ровно версии 1.56.1.
   - Проект на другой версии `@playwright/test` получает SKIPPED с причиной: установка браузеров потребовала бы сети и другого образа.
   - Тесты запускаются в копии дерева без сети: приложение поднимает `webServer` внутри песочницы.
   - Упавший тест — находка с файлом и строкой, гейт `tests`.

5. **k6.**
   - Запускает скрипты проекта: `*.k6.js`, `k6/*.js` или `performance_scripts`.
   - Без `performance_hosts` — SKIPPED.
   - Пересечённый `threshold` — находка со значениями метрик в гейте `tests`: нагрузочные тесты — тоже тесты.
   - Скрипт, который не запустился, — сбой инструмента: гейт закрыт.

6. **Копия дерева и зависимости.** Инструмент, который пишет в копию дерева, получает уже установленные `node_modules`/`vendor` проекта **копией** в этой копии дерева. Это исправляет ошибку, найденную тестом Playwright.
   - Сначала каталоги монтировались только для чтения. Ревью кода нашло две проблемы: инструменты пишут кэши в `node_modules/.vite` и `.cache` и падали с EROFS, а bind mount следовал за симлинком `node_modules` → каталог хоста (например `~/.ssh`).
   - Теперь каталог-симлинк не копируется вовсе. Ссылки внутри воссоздаются, только если они относительные и остаются внутри проекта (`node_modules/.bin`, пакеты workspace). Предел копии — 2 ГиБ.

## Последствия

- Скрипт установки может обратиться только к реестру. Попытка соединения в обход прокси не находит маршрута, DNS недоступен.
- Пакетные менеджеры (npm, pip, composer, go, cargo) используют `HTTPS_PROXY`/`HTTP_PROXY`. Инструмент, который игнорирует прокси, не получает сети.
- На каждый шаг с сетью тратится около 1–2 с на создание сети и прокси. Шаги с сетью редки.
- **Остаточный риск:** внутри туннеля `CONNECT` прокси видит только TLS. Имя сервера TLS и зашифрованный `Host` он не проверяет, поэтому через разрешённое имя на общем CDN можно обратиться к другому сайту того же CDN. Закрыть это может только TLS-инспекция с собственным CA в песочнице. Мы её не делаем: она ломает проверку сертификатов пакетных менеджеров. Список хостов поэтому держите минимальным.
- Образ Playwright велик (3,7 ГБ). Он скачивается `tools pull` вместе с остальными.

## Альтернативы

- **iptables/nftables на хосте** — отклонено: нужен root на хосте worker'а, и решение несовместимо с rootless Docker (ADR-0034).
- **Squid как прокси** — отклонено: ещё один образ и конфигурация. Собственный прокси на стандартной библиотеке умещается в 200 строк, его проще проверить, и он даёт журнал решений в нужном формате.
- **DNS-allowlist** — отклонено: не закрывает прямые обращения по IP.
