# ADR-0049: Рабочая зона агентов

- Статус: Принято
- Дата: 2026-11-07
- Уточняет: [ADR-0030](0030-server-api-rbac-queue.md), [ADR-0046](0046-ai-providers-from-web.md)

## Контекст

На странице «Агенты» все двенадцать агентов оркестратора показывались как «ещё не запускался». Пользователь не видел, как дать им задачу. Причин три:

1. **Задачу агентам ставит run.** На сервере это `develop` или `maintain` (`api/kinds.py`), а создавался такой run только из скрытого диалога «Новая задача» в «Задачах». Чат Claude Code / Codex работает по подписке пользователя сам и агентов оркестратора не вызывает (ADR-0038: `start_task` только по просьбе).
2. **Чужое имя в записях.** Developer и Reviewer работают внутри шага `develop.implement`. Движок записывает выполнение под именем обработчика `builtin.develop.implement`, поэтому их карточки оставались пустыми даже после run'а.
3. **Не все агенты доступны из веба.** Requirements, Architect, Planner и Bootstrap работают только в CREATE и MODERNIZE, а это команды CLI. QA, Performance и DevOps не подключены ни к одному сценарию (отчёт [`docs/reports/2026-11-06-ai-agents-audit.md`](../reports/2026-11-06-ai-agents-audit.md), раздел 2.1).

## Решение

1. **«Агенты» → «Рабочая зона»** — вид по умолчанию.
   - **Постановка задачи.** Задача пишется своими словами.
     - «Разработка» создаёт run `develop`: первая строка — `title`, весь текст — `body`. Можно задать базовую ветку и 1–5 кругов Developer ↔ Reviewer.
     - «Исправления» создаёт run `maintain`: каждая строка — issue «заголовок: подробности».
   - **Ход работы.**
     - Шаги run'а с понятными названиями и агентами каждого шага.
     - Выполнения агентов этого run'а: статус, время, токены, стоимость, ошибка.
     - Ожидающие согласия (`external_llm`, `pr_create`…) с «Разрешить» и «Отклонить».
     - Остановка run'а и «Уточнить и запустить заново» после ошибки.
   - **Результат** берётся из артефактов шага реализации (`implementation.json`, `change.diff`) и нового поля `results` статуса run'а: ветка, коммит, PR, итог, план, файлы, вердикт ревью, diff.
   - **«Доработать»** ставит новую задачу «Разработка», которая продолжает ветку результата: она становится базовой веткой нового run'а.
   - **Проверка провайдера.** Рабочая зона проверяет ИИ-провайдер проекта (ADR-0046) и показывает, чего не хватает: провайдер не включён, нет ключа, настройки не прошли проверку.
2. **API: `results` в `GET /runs/{id}`.** Для каждого успешного шага — только скалярные поля из белого списка: `branch`, `base`, `commit`, `sha`, `url`, `number`, `iterations`, `verdict`, `summary` (до 2000 символов). Полный вывод шага (`pr_body`, план, изменения) остаётся в артефактах, право то же: `run.view`.
3. **Привязка выполнений к агентам.** Шаги, которые запускают агентов каталога, засчитываются этим агентам:
   - `builtin.develop.implement` и `builtin.maintain.item` — Developer и Reviewer;
   - `agent.<имя>.<шаг>` — `<имя>`.

   Карточки и страница агента показывают эту работу.
4. **Честный статус.** Карточка и страница агента говорят, где он работает: рабочая зона, только CLI или «пока не подключён к сценариям».

## Последствия

- Агентов можно запустить и сопровождать из одного места, без CLI и без знания видов run'ов.
- Стоимость шага реализации видна на карточках и Developer, и Reviewer: это один шаг, разделить его расход между агентами нельзя.
- Requirements, Architect, Planner, Bootstrap, QA, Performance и DevOps по-прежнему не запускаются с сервера. Нужны серверные виды run'ов `create` и `modernize` и подключение QA к DEVELOP — это отдельные задачи.

## Альтернативы

| Вариант | Почему нет |
| --- | --- |
| Вывести вывод шагов целиком в статус run'а | Большие данные (diff, план, тело PR) на каждом опросе статуса. Белый список скаляров плюс артефакты по требованию дешевле и безопаснее |
| Записывать каждого агента внутри шага отдельным выполнением | Меняет движок и учёт расхода, расход LLM записывается по задаче. Для страницы достаточно привязки по обработчику |
| Улучшить диалог «Новая задача» в «Задачах» | Диалог только ставит run, а пользователю нужно и сопровождать его: ход работы, согласия, результат, доработка |
