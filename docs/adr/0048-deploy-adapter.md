# ADR-0048: Адаптер деплоя

- Статус: Принято
- Дата: 2026-11-06
- Уточняет: [ADR-0039](0039-nexus-web-ui.md) (страница «Деплой и среды»); опирается на [ADR-0043](0043-github-actions.md) (GitHub Actions) и на зашифрованные секреты и настройки проектов
- Пересматривает: «адаптера деплоя в v2.1 нет» (ТЗ §2): автономного деплоя в Production по-прежнему нет — деплой запускает человек, а Production ждёт второго человека

## Контекст

Изменения доходили до проекта веткой или pull request, а выпуск делал внешний CI/CD. Страница «Деплой» честно писала «не подключено». Нужен деплой из платформы, но без ослабления того, на чём она держится:

- права проверяет RBAC;
- опасная операция требует подтверждения (`ApprovalOperation.DEPLOY` входит в обязательные);
- всё видно в журнале;
- сервер не становится прокси во внутреннюю сеть.

## Решение

1. **Среда** (`deploy_environments`) — куда и как проект деплоится:
   - `github_actions`: workflow репозитория проекта с `workflow_dispatch`. Ref задаёт ветку запуска. Имя среды и ref можно передать во входах (`environment_input`, по умолчанию `environment`; `ref_input`). Есть таймаут ожидания, не больше 120 минут;
   - `webhook`: https-адрес CD-системы. Тело — JSON о деплое: `event`, `project_id`, `environment`, `production`, `ref`, `commit`, `deployment_id`, `run_id`, `requested_by`, ключи отсортированы. Заголовок `X-AI-Coding-Signature: sha256=<HMAC-SHA256 тела>` подписан секретом среды `deploy.<имя>.webhook`, а `X-AI-Coding-Delivery` несёт id деплоя. Ответ 2xx — успех; `url` из JSON-ответа (только https) становится ссылкой деплоя. Без секрета запрос не отправляется. При переименовании среды секрет переносится, при удалении — удаляется;
   - флаги: `production` (всегда с подтверждением), `requires_approval`, `require_gates` (у последнего завершённого аудита нет проваленных блокирующих Quality Gates), необязательный `health_url` (GET после деплоя должен ответить 2xx; 6 попыток).

2. **Деплой — это run вида `deploy`** (режим MAINTAIN, право `deploy.run`). Строка `deployments` отражает его для веба. Шаги run'а:
   1. `deploy.resolve` — ref превращается в коммит: через GitHub для `github_actions` и через локальный git проекта для `webhook`;
   2. `deploy.gates` — проверка Quality Gates;
   3. `deploy.approval` — подтверждение;
   4. `deploy.execute` — dispatch и ожидание итога запуска, либо подписанный webhook;
   5. `deploy.verify` — проверка здоровья;
   6. `report.deploy` — артефакт `deploy-report.json`.

   Состояния строки: `queued`, `awaiting_approval`, `running`, `succeeded`, `failed`, `cancelled`. Шаги сами пишут их и причину ошибки. Run может закончиться без последнего шага (отказ в подтверждении, отмена, падение), поэтому чтение списков сверяет строку с состоянием run'а.

3. **Подтверждение — существующий механизм оркестратора.** Для Production или `requires_approval` шаг `deploy.approval` запрашивает `ApprovalOperation.DEPLOY` с правилом `deploy.environment`. Run встаёт в `AWAITING_APPROVAL` и не занимает worker. Владелец или мейнтейнер решает через `POST /runs/{id}/approve` (`approve: false` — отказ). До решения ничего не запускается. В вебе деплой в Production требует ещё и ввести имя среды.

4. **Права:**
   - среды читает `project.view`, меняет `project.settings`;
   - деплоит `deploy.run` (владелец, мейнтейнер);
   - историю видит `run.view`.

   Доступ проверяется до разбора ввода: посторонний получает 404, не узнав даже, верен ли ввод. В одну среду одновременно идёт не больше одного деплоя. `require_gates` проверяется сразу (409 с причиной) и ещё раз перед выполнением.

5. **Деплой нельзя перехватить.** Параметры run'а — `deployment_id`, `environment_id`, `ref`. Строку `deployments` закрепляет первый run (`claim`). Run того же или другого проекта с чужим `deployment_id` падает на первом шаге.

6. **SSRF:**
   - адреса webhook и проверки здоровья — только `https://` на публичный хост. Отвергаются при сохранении: loopback, частные, link-local (в том числе метаданные облака), CGNAT, `localhost`, имена без точки, `.local`, `.internal`, `.lan`, `.home.arpa`;
   - транспорт `PublicOnlyTransport` при каждом запросе разрешает имя, требует, чтобы *все* адреса были публичными (защита от DNS rebinding), и соединяется с проверенным адресом, сохраняя имя для `Host` и TLS (SNI, проверка сертификата). Переадресации не выполняются;
   - тот же синхронный транспорт используют вызовы GitHub API ([ADR-0043](0043-github-actions.md)).

   Тесты подменяют транспорт атрибутом сервера `deploy_test_transport` (по умолчанию `None`). Переменной окружения, которая открыла бы частные адреса, нет.

7. **Веб:**
   - страница «Деплой и среды»: текущий проект или выбор проекта; карточки сред с последним деплоем (состояние, ref, короткий коммит, кто, когда, ссылки на run и внешнюю систему); «Задеплоить»; история;
   - редактор сред — для тех, у кого есть `project.settings`; секрет подписи webhook задаётся через `SecretField`;
   - остальные видят страницу только для чтения.

## Последствия

- Деплой виден в журнале (`deploy.start`, `deploy.environment.*`, переходы run'а, решения по подтверждению) и в истории проекта.
- GitHub Actions-деплой зависит от включённой интеграции GitHub проекта: выключенная интеграция — сразу 409 с объяснением.
- Тело webhook подписано, но не зашифровано. Получатель обязан проверять подпись и не доверять адресу отправителя.
- Отката (rollback) как отдельной операции нет: это деплой прежнего ref.
- Ожидание GitHub-запуска занимает worker до 120 минут. Опрос идёт раз в 10 с; временные ошибки GitHub переживаются, повторного dispatch нет.
- Внутренние CD-системы без публичного адреса пока недоступны. Если они понадобятся, нужен явный список разрешённых хостов на уровне сервера, а не флаг проекта.
