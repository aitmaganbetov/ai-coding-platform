# ADR-0034: Масштабирование и изоляция сервера — процессы API, общий rate limiter, пул БД, rootless или удалённый Docker, S3

- Статус: Принято
- Дата: 2026-11-05
- Уточняет: [ADR-0030](0030-server-api-rbac-queue.md), [ADR-0031](0031-server-deployment-storage-ui.md)

## Контекст

Нагрузочный тест S9 (ADR-0032) показал два предела:
- один процесс API упирается в GIL примерно на 100 запросах в секунду;
- увеличение пула соединений без расчёта превысило `max_connections` PostgreSQL, и прогоны терялись.

ADR-0030 оставил rate limiter внутри процесса: при нескольких процессах лимит умножался. ADR-0031 рекомендовал изолировать worker'а с доступом к Docker. Хранилище S3 было проверено только эталонной подписью и fake-сервером (B-807).

## Решение

1. **`serve --workers N`** — N процессов API на одном порту (uvicorn, фабрика `app_from_env`). Несовместим с `--with-worker`. Worker'ы масштабируются отдельными процессами или хостами.

2. **Пул БД задаётся явно:** `AI_CODING_SERVER_DB_POOL_SIZE` / `DB_MAX_OVERFLOW`, по умолчанию 10 / 10. Правило: `процессы × (pool + overflow) < max_connections`.

3. **Общий rate limiter** (`AI_CODING_SERVER_RATE_LIMIT_BACKEND`; `auto` — общий на PostgreSQL и при нескольких процессах API на одной БД, включая SQLite, `serve --workers N`: иначе каждый процесс давал бы полный лимит).
   - Счётчики по минутам хранятся в таблице `rate_limit_counters` (миграция `0003`), ключи — SHA-256.
   - Используется скользящая минута, без двойного всплеска на границе.
   - Атомарный upsert `INSERT … ON CONFLICT DO UPDATE … RETURNING` в PostgreSQL и SQLite.
   - Запись в БД на каждый запрос поставила все запросы клиента в очередь на блокировке одной строки (p95 0,4 → 1,9 с). Поэтому процесс накапливает счёт и синхронизирует его раз в 0,5 с вне своей блокировки.
   - Цена — допуск не более «скорость × 0,5 с» на процесс. Если БД недоступна, решает локальный счёт.
   - **Сбой БД не замедляет API:** после ошибки лимитер не обращается к БД в течение паузы (1 с, удваивается до 30 с), и пробует её только один запрос за раз. Раньше каждый запрос мог ждать таймаута соединения или пула.
   - **Переполнение таблицы ключей не теряет счётчики.** Раньше при `max_keys` очищалось всё, включая ещё не отправленные счета, и перебор адресов сбрасывал счёт попыток входа. Теперь сначала уходят ключи вне окна, затем ключи, полностью записанные в БД. Если и после этого места нет, неотправленные счета отправляются одной транзакцией, и только потом ключи удаляются.

4. **Docker для worker'а** — rootless или удалённый демон.
   - `docker` CLI получает только переменные подключения к демону: `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_TLS_VERIFY`, `DOCKER_CERT_PATH`, `SSH_AUTH_SOCK`, `XDG_RUNTIME_DIR`. Секреты процесса платформы туда не попадают.
   - Удалённому демону каталог данных нужен по тем же путям.
   - Временные каталоги, которые хост не может удалить, удаляет сам пользователь песочницы (S8) — это работает и для uid-отображения rootless.

5. **S3 проверяется на настоящем сервере:** VersityGW по digest проверяет SigV4 сам. Проверяются операции, постраничный `ListObjectsV2`, неверный ключ, подмена объекта и серверный прогон с артефактами в bucket'е.

## Последствия

- Горизонтальное масштабирование API и worker'ов не ослабляет лимиты и не исчерпывает соединения БД.
- **gVisor и защита демона от захвата worker'ом** — см. [ADR-0035](0035-runtime-isolation-and-release.md).
- Redis не нужен: очередь и лимиты живут в PostgreSQL. Redis остаётся необязательным по ТЗ §4 и не реализован.

## Альтернативы

- **Redis для лимитера** — отклонено: новая обязательная инфраструктура ради одной функции. Батчевый счётчик в БД дал нужную точность.
- **Запись в БД на каждый запрос** — измерено и отклонено (п. 3).
