# ADR-0024: Агенты CREATE и сценарий CREATE

- Статус: Принято (развивает ADR-0011)
- Дата: 2026-11-05
- Спринт: S5 (B-400…B-406, B-420, B-421)

## Контекст
ТЗ §6 задаёт агентов и единый контракт. FR-03 описывает сценарий CREATE: «диалог требований → версия ТЗ → approval → ADR → backlog → bootstrap». AC-01 требует получить из текстового описания согласованное ТЗ, ADR, backlog, bootstrap и PR.

## Решение
1. **Порт `Agent`** (`agents/base.py`): `name`, `title`, `requires_llm`, `output_schema`, `run(task, ctx)`.
   - Вход — `AgentTask` (контракт ADR-0011). Окружение — `AgentContext`: входы и LLM, больше ничего.
   - Результат принимается только через `validate_agent_output`.
   - Схемы выходов лежат в `ai_coding/schemas/agents/*.output.schema.json` (B-405).
2. **`LLMAgent`.**
   - Системный промпт объявляет все входы *данными* и заключает их в `<input name="…">`; закрывающий тег внутри данных нейтрализуется. Это защита от prompt injection (ТЗ §12).
   - Ответ запрашивается структурированно по схеме агента.
   - Агент выполняет **семантические проверки**, которых схема не выражает: уникальность id, ссылки на существующие требования и модули, ацикличность зависимостей, покрытие каждого FR историей, модулем и задачей.
   - При нарушениях работает **цикл исправления** — не более 2 раундов: модель видит свой ответ и список проблем и возвращает исправленный результат целиком. Если проблемы остались, задача проваливается; невалидный ответ никогда не засчитывается как успех.
3. **Агенты S5.**
   - Requirements → ТЗ: цели, FR/NFR, user stories с критериями приёмки, допущения, открытые вопросы.
   - Architect → стек, модули, ADR, API, модель данных.
   - Planner → backlog с зависимостями, оценками, приоритетами и milestones.
   - **Bootstrap детерминирован**: каркас рендерится из шаблонов, а результат LLM входит только как документация и описания модулей. Каркас воспроизводим, проходит собственные тесты и lint (это проверяется тестами). CI в нём закреплён по SHA и работает с минимальными правами.
   - Поддерживаемые стеки — Python и Node.js. Для других языков агент сообщает «не поддерживается», а не выдаёт полуработающий каркас.
   - Остальные 8 агентов перечислены в каталоге со спринтом реализации (`ai-coding agents list`).
4. **Сценарий CREATE** (`workflows/create.py`):

   ```
   create.requirements → create.approve → create.architecture → create.plan → create.bootstrap → create.verify → [git.push → github.pr → github.pr.verify]
   ```

   - **Версия ТЗ** — `v<раунд>-<sha8 содержимого>`. Approval `spec_approval` относится к конкретной версии и **не отключается** конфигурацией. Архитектура не начинается на неутверждённой версии.
   - **Диалог требований** — последовательность прогонов. «Доработать» отклоняет текущую версию (прогон CANCELLED) и запускает новый раунд с предыдущей версией и ответами на открытые вопросы. Каждый раунд — отдельный прогон в audit trail.
   - **Bootstrap.**
     - Запись идёт только в отдельном worktree на рабочей ветке (`ai/bootstrap`); основная ветка не меняется.
     - Критичные файлы (CI, конфигурация, lock-файлы) требуют одного approval `critical_file_change` со списком путей.
     - Коммит один, с trailer `AI-Coding-Run`; журнал эффектов и проба по trailer исключают повторный коммит при retry или resume.
     - Существующую ветку агент не перезаписывает.
   - **`create.verify`** перечитывает каждый файл из коммита и сверяет SHA-256 с манифестом. Шаг выполняется до push.
   - **PR** (опция `--pr`) использует workflow `pull_request` из S4: approval `pr_create`, egress-политика, без merge и auto-merge.
5. **Новый проект.** `ai-coding create --dest DIR`:
   - инициализирует git-репозиторий;
   - делает пустой корневой коммит на основной ветке, чтобы у рабочей ветки была база. `create_root_commit` разрешён только в репозитории без коммитов.
   - сохраняет конфигурацию прогонов в `.ai-coding/config.yml` (каталог исключён из git; секретов там нет — только имена переменных). Благодаря этому `ai-coding run approve/status -C DIR` работают до того, как в проекте появится свой `.ai-coding.yml`.
6. **Возобновление.** CREATE-прогон возобновляется командой `ai-coding create --resume`. Универсальный `run resume` отказывает с подсказкой — так же, как для PR (S4).

## Последствия
- **Плюс:** каждый артефакт CREATE (ТЗ, ADR, backlog, каркас) проверяем машинно и связан ссылками с требованиями.
- **Плюс:** человек утверждает конкретную версию ТЗ и отдельно — критичные файлы.
- **Ограничение:** качество ТЗ и архитектуры зависит от модели. Детерминированные проверки ловят структурные ошибки, но не оценивают смысл, поэтому и нужен approval.
